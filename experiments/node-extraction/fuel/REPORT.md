# Indian petrol-pump receipt extraction - generalisation experiment: report

> **CORRECTION NOTICE (added in phase 2).** The synthetic labels used in this report credited a brand-only pump name ("NAYARA ENERGY", "IOCL", "HP") as an exact match even when a dealer name was printed, which contradicts the scoring policy. Every synthetic `pump_name` exact figure below is therefore inflated (false-accept and false-confident figures are not). Corrected first-look figures: `reports/RESULTS_PHASE2.md` section 6. Authentic labels are PROVISIONAL (assistant-read, not human-verified); the phrase "assistant-verified" in this document means that. See `REPORT_PHASE2.md`.

Scope: `pump_name`, `transaction_date`, `total_amount` only. Experimental interface only; nothing was connected to the Spinco backend, staged, committed,
packaged, versioned or released. All tables are generated by `scripts/make_report.mjs` from the stored runs (`reports/RESULTS.md` has every number, with
numerators and denominators); this file interprets them. Read the "How much to trust this" section first.

## 1. Bottom line

* **Not ready for production use.** On authentic receipts the improved extractor almost never gives wrong values *silently*, but it also automates almost nothing:
  of 22 authentic receipts it accepted 1 without review (correctly) and sent 21 to review. It is a **pre-fill-and-evidence aid for a reviewer**, not an automatic reader.
* The real gain is **safety, not accuracy**: false accepts on the 22 authentic receipts fell from 13 (59%) with the existing pipeline to 0, and 22 of 24 non-fuel
  controls that the existing pipeline accepted are now held for review (0 accepted). Pump-name exact match rose from 2/21 to 11/21; amount from 15/22 to 17/22; date
  exact match fell from 18/22 to 16/22 because the old parser guesses day-first on ambiguous dates and the new one refuses to (see 5).
* **Every authentic number is optimistic or tiny**: 22 receipts, three brands (BPCL 12, HP 6, IndianOil 4), 7 reports, labels read by the assistant (not independently human-verified), and
  all 22 are now "consumed" (fixes were made after seeing them). There is **no authentic Nayara, Jio-bp or Shell receipt**; those brands are exercised only by synthetic receipts.
* No claim is made about handwriting. No model was trained.

## 2. What was done (in the brief's order)

1. **Inspected** git (branch `master`; `experiments/` is wholly untracked) and the experiment before editing; preserved it (SHA-256 manifest of 109 files + full copy in
   `experiments/_preservation/`). "Node" is a Node.js program of deterministic rules + tesseract.js OCR + pdfjs - not a trainable model (`AUDIT.md`). **Re-verified at the end: 0 of the 109 pre-existing files changed, none missing, no new file outside `fuel/`.**
2. **Researched sources** (`sources.json`, `RESEARCH.md`): **no public dataset of authentic Indian petrol receipts was found.** Public Indian fuel-receipt material is bill *generators*
   (OnlineBiller, BillCopy: simulated, no licence for outputs); `fuelbill.in` was unreachable (HTTP 530 twice). SROIE and CORD are non-Indian shop/restaurant receipts and were not downloaded.
3. **Built a corpus** by layout family, not brand: 22 authentic physical receipts found by a read-only census of the 8 approved reports and labelled by reading each page image; 1 page that matches public
   generator layouts, kept **out** of the authentic group; 78 synthetic fuel receipts (13 invented layouts, 8 degradations); a second synthetic held-out set (48, 8 new layouts, written after the first look); 24 synthetic
   non-fuel controls (some with brand-word traps: "HP Authorised Service Centre", "The Shell Beach Restaurant", "BP Chemists"). Dev / held-out are split by whole layout family; the split, the generator hash and the
   extractor hash were frozen before each first held-out run (`corpus/split_freeze.json`, `reports/FROZEN_*.json`).
4. **Baseline first**: the existing pipeline, unmodified, single-pass OCR (`reports/baseline-*`).
5. **Improved extractor** (`src/fuelExtractor.mjs`, `README.md`): evidence-aware candidate selection with raw text and source lines, explicit ambiguity, per-field review flags, and an optional bounded OCR retry (the production
   grey-contrast-threshold preprocessing and 90/-90/180 rotations, only when the first pass looks unusable). The simplest approach that worked; no pretrained receipt model was evaluated (licence/privacy/hardware not established; the 8 GB, no-GPU machine) and **no training** was justified or done (22 authentic labels).
6. **Evaluated** dev / held-out / controls separately with numerator and denominator, then attributed gains to OCR vs parser (section 4).

* The synthetic first looks are **not** clean zeros: 5/48 (held-out2) and 4/48 (held-out, after the label correction below) records were falsely accepted by the extractor as first written. The causes were a printed `Dealer:`
  label left in the name, an OCR-misspelt brand ("NAVARA ENERGY") accepted as a dealer, a "NAME - CITY" header taken whole, a garbled greeting taken as a name, and a digit misread (500.00 read as 500.60) at moderate confidence.
  After those generic fixes the same sets show 0 false accepts, but they are then development data.
* **Label-policy correction (disclosed):** 7 of the first held-out set's 8 "false-confident pump names" were my own label error (the jio-bp / Shell synthetic labels demanded `<brand> <dealer>` and rejected a correct dealer-only name).
  Fixed in `build_annotations.py`; the generator and images are unchanged; both scorings are in `RESULTS.md`.
* **Synthetic never stands for authentic.** Synthetic results are not combined with authentic ones anywhere.
* Difficulty (authentic, consumed, tiny n): e.g. dark background 5/9 pump, photographed 7/14, scanned pages 4/7, sideways margin text 2/5; blurry/faint 0/1; the rotated handwritten page now reads its printed letterhead but not the handwritten date or amount.
  By layout family and synthetic degradation: `RESULTS.md` section 4. Several families with n of 1 to 8 - treat as anecdotes.

## 4. What improved the numbers (attribution)

| authentic 22 (consumed) | pump exact | date exact | amount exact | false accept |
|---|---|---|---|---|
| old parser + single-pass OCR (= baseline) | 2/21 | 18/22 | 15/22 | 13/22 |
| old parser + OCR retry | 2/21 | 19/22 | 14/22 | 13/22 |
| new parser + single-pass OCR | 9/21 | 15/22 | 18/22 | 0/22 |
| new parser + OCR retry (= final) | 11/21 | 16/22 | 17/22 | 0/22 |

The **parser** supplies almost all of the safety and most of the pump-name gain; the **OCR retry** adds a little (it makes the large-print receipt and the rotated page readable and is neutral-to-slightly-mixed on others).
Same pattern on 126 synthetic receipts. Timing and hardware: single pass mean 0.64 s/image, retry mode mean 1.8 s, p95 6.0 s, **worst 39.8 s**, 57 of 173 images triggered the retry (including most of the 24 non-fuel controls,
which never look like fuel receipts); the extractor itself ~1 ms. Intel i3-1005G1, 4 logical cores, 8 GB, CPU only, no network. A production use would need a time budget on the retry.

## 5. Dates (the sharpest finding)

On the 22 authentic receipts, 6 print a date whose day and month are both <= 12 and nothing on the receipt proves the order. The existing parser returned a date for 5 of them (3 treated as usable) by assuming
day-first - and every guess happened to be right here. The new extractor returned a date for 2 (each justified by a month printed in the bill number, e.g. `Bill No: Sep-894177` with `02/09/2026`) and held 4 for review with both readings kept.
So the old parser's higher date score is partly unearned confidence; the new one is deliberately unable to rely on a convention it cannot prove. On the 16 receipts a careful reader can date from the receipt alone, exact match was 13/16 (old) vs 14/16 (new).
**One decision for you:** the bill-number-month rule is a receipt-template convention I observed (every `Bill No: <Mon>-...` in this corpus agrees with the printed date); I treat it as explicit evidence because the month is printed on the receipt,
but it is template-specific. If you do not want it, those 2 receipts return to review.

## 6. How much to trust this

* **n is tiny and the labels are the assistant's.** I read the authentic page images in this conversation to label them. If company receipts must not be looked at by an AI assistant at all, treat the authentic labels as unusable and re-label by a person; a human spot-check is recommended either way.
  The 22 authentic receipts share photographers, scanners and POS printers, so they are less independent than 22 suggests.
* **"Held-out" is weaker than it sounds.** Labelling required looking at every page, so the held-out *layouts* were known to me; only OCR behaviour and failure modes were unseen. All authentic receipts are now consumed.
* **Synthetic receipts were written by the same author as the extractor** and rendered by one generator; they measure robustness to what I thought of, not real-world coverage.
* **Thresholds are heuristics chosen on development data** (word confidence 0.8 for names, 0.7 for digits, line confidence 0.55/0.6). `confidence` is labelled `heuristic_uncalibrated`; no calibration study was possible.
* **Unfamiliar wording/layouts are not read**, by design returning null + review: `Net Payable`, a column-header table (0/6 amounts), a pump name that is not printed, dotted 2-digit-year dates, handwriting. They were measured, not hidden.
* The existing census saw receipts only from the approved reports; payment-app screenshots (a different document type) were excluded.

## 7. Things to know

* **ER-41115 page 50** ("Bharat Petroleum ... WELCOME!!!", blank FCC/FIP/NOZZLE rows, 'Save Fuel, Save Money', a crumpled texture, `AMOUNT: 1000`) has the layout of the public generator sites' templates. I did not count it as authentic and I am **not alleging anything**; a person should look at it.
* On the very first OCR run tesseract.js downloaded its public English language data (5.2 MB) from a CDN; no receipt data was sent. It now reads a local copy and `scripts/verify_offline.mjs` proves no network use (disclosed in `README.md`).
* `experiments/` is untracked; the new work is only under `experiments/node-extraction/fuel/`, plus `experiments/_preservation/`. The backend and the earlier generalisation work were not touched by this task.

## 8. Recommendation

Do not integrate yet. Before a later, separately authorised integration: (1) collect more authentic receipts, especially Nayara, Jio-bp, Shell and independent dealers, from more printers and photographers; (2) have a person independently verify the labels;
(3) improve the OCR layer (the dominant error source: dark backgrounds, overlay and sideways text, large print) within a time budget; (4) decide the bill-number-month policy; (5) if thresholds are to mean probabilities, run a calibration study.
`INTEGRATION_NOTES.md` states how the three fields should and should not be used to match a claim (category stays authoritative; a fuel receipt never verifies a claim by itself; ambiguous or unread -> review). **The brief was cut off mid-sentence in its section 11**; please confirm the last rule there.
