# Human verification of the three required labels (`pump_name`, `transaction_date`, `total_amount`)

## Status today: **no label in this corpus is human-verified.**
* The 22 authentic labels (and the 1 suspected-template page) were read **by the assistant from the page images**. They are **PROVISIONAL** (`annotation_status: provisional_assistant_read`).
  They have not been checked by any person, so no report may call them verified or ground truth.
* Synthetic and control labels are exact by construction (`construction_truth`); they say nothing about real receipts.
* It is **not known** whether company policy permits an AI assistant to review these receipts (`label_policy.json`: `ai_review_of_company_receipts_permitted: unknown`).
  If it does not, run `node scripts/set_label_policy.mjs --assistant-labels exclude --ai-review no --confirmed-by "<name, role>"`:
  every assistant-read label is then withheld from scoring (`excluded`) until an authorised person has relabelled it, and the authentic metrics become 0/0 rather than misleading.

## How a person verifies labels
1. `node scripts/build_review_pack.mjs` (existing receipts) and/or `--scope pending` (newly intaken receipts). The pack is **blind** by default (provisional labels hidden).
   It is a static folder: `review.html` (works offline, no network access), `manifest.js`, `INSTRUCTIONS.txt` and `review_sheet.csv`; images are referenced, not copied. **`review_sheet.csv` is only a paper worksheet: there is NO importer for it** (nothing reads it; `tests/review_pack_instructions.test.mjs` guards that claim), so answers written in it are not recorded or verified. The **only** accepted submission is the JSON exported by `review.html`.
2. The reviewer (authorised by the company) opens `review.html`, enters their id, ticks the authorization box, and for each receipt records: the pump/station name (or logo-only / not printed / illegible),
   the transaction date as printed + as YYYY-MM-DD + whether the day/month order is provable **from the receipt alone** (and how), and the total amount (or illegible). Then **Export JSON**.
   - Choosing `illegible` / `not printed` **clears that field's value immediately** (the printed-text box is kept), and the saved state is updated at once.
   - **Export JSON is blocked, with a visible message, until every completed receipt passes the same rules `apply_verification.mjs` enforces** (the page embeds `src/reviewValidation.mjs` verbatim; the pack's `manifest.js` records its SHA-256 as `validator_sha256`). A receipt with no statuses chosen is left out of the export, as before; an invalid one blocks it. Messages name the receipt and rule, never the values.
   - Packs generated **before** this change (e.g. `review-pack-20261020/`) have the old behaviour and must be regenerated before real use.
3. `node scripts/apply_verification.mjs <export.json> [<second reviewer>.json]`
   - **validates every export before writing anything**; one invalid export or entry rejects the whole invocation (exit 1, nothing written; messages name the receipt and field, never the reviewer's values):
     - `reviewer_id`: 3-64 characters, ASCII letters/digits/space/`.`/`_`/`@`/`-`, starting and ending with a letter or digit; whitespace is trimmed and collapsed; `+` is reserved. It is **self-attested text**;
     - `authorization_confirmed` must be exactly `true`;
     - statuses must be the ones the review tool offers - pump: `read | logo_only | not_printed | illegible`; date: `read | illegible`; amount: `read | illegible`;
     - `read`/`logo_only` need a non-empty value; a `read` amount must be a number > 0 (at most 10,000,000, at most 2 decimals); `illegible`/`not_printed` must not carry a value (clear it or choose `read`);
     - the date must be a real calendar date written `YYYY-MM-DD` (years 1990-2100 as a sanity bound; no other format is accepted, none is guessed or inferred);
     - the day/month-order claim must agree with its evidence: "provable from the receipt" cannot cite `other_documents`/`none`; "not provable" cannot cite receipt-intrinsic evidence; `component_gt_12` needs a day > 12; `equal_components` needs day = month;
   - **source-type eligibility (fail closed):** only receipts the corpus classifies as `authentic` or `suspected_template_generated` (`corpus/annotations.json` `source_type`), or intake receipts with `authentic_issued_receipt` provenance, may be named. `synthetic` and `generic_control` records (construction truth), and any unknown or missing source type, reject the whole invocation. Eligibility is never inferred from a receipt id's spelling or from anything in the export; `src/labels.mjs` applies the same rule when loading (an overlay for an ineligible record is ignored and counted in `summary.ignored_ineligible_overlay_entries`, and `applyReviewerEntry` refuses it);
   - the same reviewer (compared case-insensitively on the normalised id) may appear **once** per invocation; a duplicate is rejected - one person is never counted as two reviewers;
   - with two or more reviewers, a receipt is verified only if they agree on **every** required field (status and value of pump, date, amount, and whether the date order is provable from the receipt); otherwise it is appended to `corpus/adjudication_needed.json` and stays unverified;
   - **never overwrites** an existing verified record: a later review that agrees is a no-op; one that disagrees is recorded as an `open` event in `corpus/review_conflicts.json` (exit code 3) and `src/labels.mjs` then holds that receipt back from `human_verified` (`summary.held_by_open_conflict`) until a person adjudicates it. The script never resolves or deletes conflicts;
   - adjudication, conflicts and `corpus/review_history.json` (every invocation: reviewers, SHA-256 of each export, outcomes) are append-only;
   - writes `corpus/verified_labels.json` (who, when, the values, `reviewer_count`, `second_reviewer_agreed`, and field-level agreement with the provisional labels - the first honest measure of how reliable the assistant's reading was).
4. `run_eval` / `make_report` then show, per group, how many labels are human-verified vs provisional, and `--labels verified_only` scores only the verified ones.

## What is NOT enforced (read before relying on a "verified" label)
* **Reviewer identity is self-attested.** The id is typed into the review tool; nothing proves who the person is. Every verified record says `identity_assurance: "self_attested"`.
* **`label_policy.json` `authorized_reviewers` is NOT consulted** (it is currently `[]`). Authorization is only the reviewer's own `authorization_confirmed` tick. Enforcing an allowlist needs a policy decision (who maintains it, how ids are matched) and is not done here.
* A single reviewer is still sufficient to verify a label (existing policy; `second_reviewer_agreed` / `reviewer_count` show whether it was double-checked). Two-reviewer review is recommended, not required.
* Open questions the tests do not decide: whether `order_provable_from_receipt: true` should *require* an evidence value (today it may be left empty), and how an open conflict is formally closed (today: a person adjudicates outside the tool; the tool never edits or deletes the conflict log).

## Malformed intake-register entries
`src/intakeRegister.mjs` is the single definition (used by `src/labels.mjs`, `scripts/apply_verification.mjs` and `scripts/build_review_pack.mjs`) of a **usable** register entry: an object with a non-blank text `receipt_id` (no surrounding whitespace, at most 120 characters), an `image_path` that is a relative, forward-slash path inside `corpus/authentic_intake/` (no `.`/`..`/empty segments), `provenance` that is an object with `source_type: "authentic_issued_receipt"`, a `split` that is exactly `development` or `heldout_untouched` (the two values `register_intake.mjs` writes; anything else - including a typo - is **not** silently treated as development any more), a non-blank text `receipt_family`, an id that appears **once** in the register, and an id that does **not collide** with an `annotations.json` record - and it must not take part in any of these cross-entry conflicts. Eligibility is never inferred from an id's spelling.
* **Cross-entry conflicts (pure, from the register alone; every member of a conflicting group is unusable, so no entry can become eligible by being first or by looking valid):**
  * **duplicate `image_path`** - compared after Unicode NFC normalisation and case-folding (NTFS paths are case-insensitive); only paths that pass the path check are compared;
  * **duplicate `sha256`** - the same image registered twice; only **well-formed** hashes (exactly 64 lowercase hex characters) are compared. Missing or malformed hashes are *not* treated as duplicates here; they are refused at the integrity boundary (see below);
  * **a `receipt_family` that appears under both splits** - the family identifier is the required `receipt_family` field that `register_intake.mjs` copies onto every entry and compares by **exact string equality** when it enforces "a family goes wholly to one side" (`intake/INTAKE.md` step 2). The validator applies the same rule to the register as a whole, so a hand-edited register cannot put a family on both sides. Entries that are otherwise invalid still count (an invalid entry declaring the opposite split blocks the valid ones). **Not detected:** spelling variants (`Fam_A` / `fam_a` / ` fam_a`) are different families to the writer and to this check, and a family shared between the intake register and `annotations.json` is not compared - nothing in the schema links them, and nothing is guessed from ids or names.
* **Unusable entry** (anything else): skipped by the loader, announced on stderr and counted (`summary.skipped_intake_entries` / `skipped_intake_detail`); never scored, run, offered in a pack or human-verified. An export naming it is rejected before any write (the whole invocation, as for any invalid export). Duplicate ids block **all** entries with that id; an id that collides with an annotation record blocks **both** (the id is ambiguous, so that annotation record cannot be verified until the register is repaired).
* **Unusable register** (file unreadable / not JSON / top level not an object / `receipts` missing or not a list): the loader loads no intake receipt (warns, `summary.intake_register_status: "invalid"`, never throws); `build_review_pack.mjs` writes no pack (exit 1); `apply_verification.mjs` rejects the invocation before any write (exit 1). No register file at all is normal (`"absent"`).
* **Three different properties - do not conflate them:**
  1. **Structural validity** (everything above): a pure property of the register text, independent of the filesystem. `src/labels.mjs` depends only on this: a structurally valid entry whose image is missing **still loads as a pending record**.
  2. **Image availability**: a filesystem property, checked only at the I/O boundaries by the shared `intakeImageProblem(fuelDir, entry)` in `src/intakeRegister.mjs`. The path must resolve - `..`, symlinks and junctions included - to a **regular, non-empty file inside `corpus/authentic_intake/`**; a missing file, directory, zero-byte file, broken link, or a link that escapes the folder is *unavailable* (it never reads image bytes and never throws). (Offering and applying use the combined availability + integrity check described in 3.) `build_review_pack.mjs` does not offer an unavailable receipt (warning `not offered (<reason>)`); `apply_verification.mjs` rejects the **whole invocation before any write** if any **named** usable intake entry is unavailable - including one that is already verified - and reports `receipt <id>: <reason>` together with any ineligible ids. An unavailable image for an id the export does not name blocks nothing.
  3. **Image integrity**: checked at the same two boundaries by the shared `intakeImageIntegrityProblem(fuelDir, entry)` in `src/intakeRegister.mjs` (availability first, with exactly the reasons above; then the hash). Contract, taken from the only writer (`scripts/register_intake.mjs`): `sha256` is the **lowercase hex SHA-256 of the raw bytes of the stored image** (the stored copy is written from the very bytes that were hashed). It must be present, exactly 64 lowercase hex characters (no case folding, trimming or rewriting - anything else is *malformed*), and equal to the hash of the file's bytes. A **missing or malformed hash is unverifiable and refused** (fail closed - the writer always emits a valid one); a mismatch reports `image integrity check failed (… registered <12 hex>…, actual <12 hex>…)` and never prints image content. The bytes are read only for entries that are being offered or named, in 1 MiB chunks, from the same resolved file the availability check approved. `src/labels.mjs` and the structural validator never read image contents: an entry with a bad hash still **loads as a pending record**, it just cannot be offered or verified. Applier: any failing named entry - including an already-verified one whose image changed after verification - rejects the whole invocation before any write (exit 1, no conflict event, no history).
  * **Limits of this control:** it ties the file to the *register entry*, not to what a reviewer saw (an image replaced and restored between review and apply goes unnoticed), and it is **not tamper-proof against someone who can edit both the image and the register** (they can recompute the hash); protecting the hash itself needs a trust root outside these files (see the policy proposals on integrity hashes).
* **Consistency (tested):** for intake receipts the pack offers a receipt if and only if the applier would accept it (same eligibility function, same integrity helper), once each, with its own image path. Intake receipts appear only for `--scope pending|all` (a scope choice, not a validity rule); already human-verified receipts are not offered again. The one-way exception is the scope: the default `authentic` scope never offers intake receipts, although the applier would accept a usable, intact one.
* **Held-out lock (`scripts/lock_heldout.mjs`)** now uses these same checks (see `intake/INTAKE.md` step 5): it refuses unless the register is valid in full and every **held-out** entry's image is available and matches its registered SHA-256; it refuses to create an empty lock; and it never overwrites, repairs or deletes an existing lock (exclusive creation; no recovery procedure exists). Covered by `tests/lock_heldout_hardening.test.mjs`. Still **not** covered by the lock: `lockStatus` compares only the four code files, so a held-out image or label changed *after* the lock is not detected by `run_eval`'s lock report; the lock file itself is plain JSON with no integrity anchor.
* **Evaluation (`scripts/run_eval.mjs`)** now runs a preflight (`src/evalPreflight.mjs`) **before any OCR and before any report is written**; any problem makes it exit 1 with the reasons and leaves everything untouched. It refuses when: a command-line value is unknown (`--only`, `--impl`, `--ocr`, `--labels`, or an unsafe `--label`, which names files under `reports/`); the intake register is invalid or has **any** skipped entry (conflicting duplicates, family on both splits, malformed entries - dropping intake receipts silently would mislead); nothing is selected; a selected image is missing, empty, or (intake) does not match its registered SHA-256 (corpus images must exist as non-empty files inside `corpus/` - they carry no per-image hash, so none is checked); `corpus/ocr-index.json` is unreadable (it was read only after all the OCR); a held-out lock file exists but is malformed; or held-out **intake** receipts are selected and there is no valid lock, or the register's held-out entries differ from the lock (ids, `sha256`, `receipt_family`, `brand_family`) - which catches an image or register entry changed after locking against the **lock**, not just the register. Scoring, thresholds and metrics are unchanged; for valid inputs the console output, both report files and the OCR calls are identical to the previous version (compared on synthetic mirrors). Covered by `tests/run_eval_preflight.test.mjs`.
* **What the lock protects.** `heldout_lock.json` records, per held-out receipt, the `sha256` / `family` / `brand` copied from the register when it was created (and checked against the image bytes at that moment by `lock_heldout.mjs`), plus the hashes of four code files. `lockStatus` itself verifies **only the code hashes** (and a changed extractor still only *reports* that the set is now development data; it does not block). The image hashes in the lock are now compared by `run_eval`, but the lock is plain unanchored JSON: it proves what was **recorded**, not that nobody edited the lock, the register and the images together; a lock created before the lock script was hardened never had its hashes verified at creation. Labels are not covered by the lock.
* Not covered: `register_intake.mjs` reads the register directly and assumes it is well formed. An existing report with the same `--label` is still overwritten by a valid run (unchanged behaviour); the two report files are written one after the other, not atomically. Covered by `tests/intake_register_validation.test.mjs`, `tests/intake_image_integrity.test.mjs`, `tests/intake_loader_robustness.test.mjs` and `tests/run_eval_preflight.test.mjs`.

## How the workflow is tested without real data
`tests/helpers/syntheticMirror.mjs` copies only the scripts/modules the workflow needs into a fresh directory with synthetic fixtures (blank 1x1 images, invented dealers). The copied scripts derive their data directory from their own location, so they read and write only the mirror. `tests/synthetic_e2e.test.mjs`, `tests/review_source_eligibility.test.mjs` and `tests/review_ui_export.test.mjs` use it (OS temp by default; `FUEL_SYNTHETIC_E2E_ROOT` keeps mirrors in a chosen folder). `tests/review_tool_smoke.py <review.html>` drives a synthetic pack in a real browser. Never point it at a real pack.

## Guarantees (tested in `tests/verification.test.mjs`, `tests/review_export_hardening.test.mjs`, `tests/reviewValidation.test.mjs`, `tests/review_source_eligibility.test.mjs`, `tests/review_ui_export.test.mjs`, `tests/synthetic_e2e.test.mjs`)
* No script or test can mark a real label verified without a well-formed reviewer id and an authorization confirmation; invalid overlay entries (bad id, unsupported status, inconsistent status/value, impossible date) are ignored and counted, and `applyReviewerEntry` refuses them.
* An `illegible` field is excluded from scoring (never replaced by a guess) and can never be called a false-confident error.
* The reviewer's value replaces the provisional one; the provisional value is kept (`provisional_label`) for audit.
