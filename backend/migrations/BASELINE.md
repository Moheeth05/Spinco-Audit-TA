# Adopting Alembic on an already-existing database (dev or production)

This project's SQLite databases (both the local dev DB and the production
DB at `%APPDATA%\Spinco TA Audit\database\spinco_ta.db`) were created by
`Base.metadata.create_all()`, never by a migration tool. Alembic is being
introduced now, on top of that existing state, **not** replacing it.

## The baseline migration

`migrations/versions/31e67f71b14d_baseline_current_schema_as_is.py` was
generated by autogenerating against a **fresh, empty** database (not the
real dev/production DB) — it is a pure `CREATE TABLE ...` migration that
reproduces the current models exactly, so it is:

- **Safe to run with `alembic upgrade head`** against a brand-new, empty
  database (e.g. a future fresh PostgreSQL instance, or a fresh test DB).
- **NOT safe to run with `alembic upgrade head`** against a database that
  already has these tables (it will fail — `CREATE TABLE` on an
  already-existing table).

## How to onboard an existing database (dev, and eventually production)

Use `alembic stamp head` instead of `alembic upgrade head`. `stamp` does
**no DDL at all** — it only writes one row into a new `alembic_version`
bookkeeping table, marking "this database's schema already matches
revision X." It never touches any existing table or row.

```powershell
cd backend
$env:SPINCO_DB_PATH = "<path to the database to onboard>"
.\.venv\Scripts\alembic.exe stamp head
```

This was already done, verified, for the **local dev database**
(`backend/spinco_ta.db`) as part of introducing this migration
infrastructure: hash-compared before/after, row counts confirmed unchanged
(only the new `alembic_version` table was added).

## The production database — NOT done in this task

The exact same one-line `alembic stamp head` command (pointed at
`SPINCO_DB_PATH=%APPDATA%\Spinco TA Audit\database\spinco_ta.db`) is what
onboards production once that's explicitly approved. It carries the same
safety property demonstrated on the dev DB — no DDL, no data touched, only
one bookkeeping row added — but running anything against the live
production database requires its own explicit approval and is out of scope
for this task (see `docs/CENTRALIZED_ARCHITECTURE.md` §29).

**Before stamping production**, take a fresh timestamped backup first (same
discipline already established elsewhere in this project's operational
history) purely as a safety margin — `stamp` itself doesn't modify data,
but any first real use of a new tool against production data warrants one.

## After baselining: applying real schema changes

Once a database (dev now; production later, after approval) is stamped at
the baseline revision, **future schema changes go through a normal Alembic
migration** (`alembic revision --autogenerate -m "..."` then
`alembic upgrade head`) instead of the old hand-rolled
`app/services/db_migrations.py` approach. That module still runs today
(nothing about it was removed in this phase) — new schema changes should
use Alembic going forward; retiring `db_migrations.py` entirely is a
follow-up, not done here since its existing hand-managed columns are still
in active use and migrating that history into Alembic cleanly deserves its
own deliberate pass.
